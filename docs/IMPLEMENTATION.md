# 项目实现方式

本文档介绍 YVR Bridge 的整体设计思路、组件关系及应用适配流程。具体构建和部署操作请查看 [DIY 构建与新增应用](BUILDING.md)。

## 1. 整体思路

不同 Android XR 设备可能使用不同的 OpenXR Runtime、扩展集合、输入绑定和系统环境。为一个平台开发的应用在另一个平台上运行时，可能遇到初始化失败、设备识别异常、输入不可用或画面显示不正确等问题。

YVR Bridge 采用应用级兼容方案，在需要适配的位置介入应用与 OpenXR 运行环境之间的调用流程，并根据具体应用的问题选择相应补丁。

## 2. 主要适配方向

### OpenXR 接口适配

针对不同 Runtime 的接口行为和扩展差异，分析应用使用的 OpenXR API，并对确实存在兼容问题的调用进行适配。

### 原生动态库代理与补丁

通过原生动态库层面的代理或补丁处理应用的特定调用路径。具体采用何种方式，应由目标应用的依赖结构和问题表现决定。

### 设备与系统兼容

部分应用可能会检查设备型号、系统版本或平台标识。遇到此类问题时，应先确认检查发生的位置及其用途，再决定是否需要应用级兼容处理。

### 输入与显示适配

针对控制器绑定、交互配置、纹理格式、投影方向及图层合成等问题，按应用实际调用路径进行验证和修复。

## 3. 典型工作流程

```text
目标 XR 应用
    |
    v
应用原生库 / OpenXR 调用
    |
    v
YVR Bridge 兼容层及应用补丁
    |
    v
OpenXR Loader
    |
    v
目标设备 OpenXR Runtime
    |
    v
头显显示与交互
```

这是用于理解项目的逻辑示意图。实际拦截位置和调用关系可能因应用、构建版本及设备环境而异。

## 4. 应用级补丁原则

- 不假设所有应用都需要相同的补丁。
- 优先定位具体故障及其发生的调用阶段。
- 将应用专用逻辑与通用适配逻辑分开。
- 明确记录补丁适用的应用版本和设备环境。
- 保留原始文件与可回退方案。
- 不将启动成功等同于完整兼容。
